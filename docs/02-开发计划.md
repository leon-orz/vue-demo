## 1. 技术选型与理由

### 1.1 总览

| 层         | 选型                              | 说明                                                                                             |
| ---------- | --------------------------------- | ------------------------------------------------------------------------------------------------ |
| 桌面壳     | Tauri 2                           | 安装包小、内存占用低，Rust 侧可直接写系统能力与网络采集，sidecar 机制适合内嵌 mihomo 内核        |
| 前端框架   | Vue 3 + TypeScript + Vite 8       | Tauri 官方脚手架一等支持；`<script setup>` + Composition API；Vite 用最新稳定版 8.x（Rolldown 内核），详见 1.4 |
| 状态管理   | Pinia                             | Vue 3 官方推荐，TS 类型友好                                                                      |
| 组件与样式 | **shadcn-vue + Tailwind CSS**     | 不使用成品 UI 库，见 1.2                                                                         |
| 本地存储   | SQLite（sqlx，Rust 侧独占）       | 配置与用量缓存；schema 收归 `crates/core/migrations/`，由 Rust 按版本号迁移执行，前端不直连数据库 |
| 密钥存储   | **keyring-rs**                    | 见 1.3                                                                                           |
| 图表       | ECharts                           | 仪表盘、用量趋势；按需引入控制包体积                                                             |
| 代理内核   | mihomo sidecar                    | 随安装包分发，RESTful API（默认 9090）驱动                                                       |
| 包管理     | pnpm workspace + Cargo workspace  | monorepo 双 workspace，见第 2 节                                                                 |

### 1.2 组件方案：shadcn-vue vs 纯 UnoCSS 手写

已确认：**不使用成品 UI 组件库**（Naive UI / Element Plus 均排除）。两个候选：

| 维度       | shadcn-vue（选定）                                                              | 纯 UnoCSS 手写组件                     |
| ---------- | ------------------------------------------------------------------------------- | -------------------------------------- |
| 本质       | 组件以**源码形式**拷进仓库（基于 Reka UI 无头组件 + Tailwind），归项目所有      | 只有原子化 CSS 引擎，组件全部从零写    |
| 现成度     | Button/Dialog/Select/Table/Tooltip 等开箱可用，可随意改                         | 每个组件自己造，工作量大               |
| 可访问性   | Reka UI 处理焦点管理、键盘导航等                                                | 自己处理，容易留坑                     |
| 暗色模式   | Tailwind `dark:` 变体，主题定制极方便                                           | 同样方便，但组件样式要自己设计         |
| 依赖负担   | 无运行时库依赖，代码就在仓库里                                                  | 最轻，但时间成本高                     |

**结论：shadcn-vue + Tailwind CSS**。它不是传统意义上的"UI 库依赖"，而是一套拷进仓库的组件源码，既满足"不用 UI 库"的诉求，又不用从零造 Dialog/Select 这类容易出可访问性问题的组件；暗色模式用 Tailwind `dark:` 即可。**注意：shadcn-vue 依赖 Tailwind，因此不混用 UnoCSS**。图表仍用 ECharts 按需引入。

### 1.3 密钥存储：keyring-rs（已定）

S1-1 已用 keyring-rs 落地：直译"敏感 key 存系统钥匙串"的需求，桌面端走 Windows 凭据管理器（**注意：keyring 3 默认不启用任何平台后端，需显式 `features = ["windows-native"]`**，否则会静默退化为 mock 内存存储——S1-1 实测踩过此坑）；无桌面环境侧（如 hub）封装同一 trait，底层退回"主密钥加密的文件存储"，接口不变。备选 stronghold（加密快照文件）因引入额外概念已排除。

### 1.4 基础环境与版本清单（已确认）

| 项         | 版本/方案                                                          | 说明                                                                                                                   |
| ---------- | ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| Node.js    | **24 LTS**                                                         | active LTS，生命周期长；Tauri 2 要求 ≥ 20.18                                                                           |
| pnpm       | 最新稳定版，corepack 管理                                          | `package.json` 写 `packageManager` 字段锁死版本                                                                        |
| Rust       | stable 最新（rustup 管理）                                         | 已安装 1.98.1；crates.io 走 rsproxy 国内镜像（`~/.cargo/config.toml`）                                                  |
| Vite       | **8.x 最新稳定**                                                   | Rolldown 内核；Tauri 适配：固定 dev 端口 1420、`clearScreen: false`、`build.target` 对齐 Windows WebView2 Chromium；ECharts 等大包手动分包 |
| Tauri      | 2.x 最新稳定                                                       | `tauri build` 出 Windows NSIS 安装包，mihomo sidecar 随包分发（仅 Windows 二进制）                                      |
| TypeScript | strict 全开                                                        | 前后端共享类型由 ts-rs 生成，invoke 参数/返回类型禁止手写                                                              |
| 版本锁定   | lockfile 锁定（Cargo.lock + pnpm-lock.yaml 提交入库）              | 两台开发机与 CI 装出一致结果                                                                                           |
| 编辑器     | 仓库内置 `.editorconfig` + VSCode 推荐配置                         | 换电脑开箱即用                                                                                                         |

### 1.5 关键架构原则

- **数据获取层可替换**：定义 `DataSource` trait（Rust），实现 `DirectSource`（客户端本地采集）与 `HubSource`（预留未接线）。UI 层面向接口编程，切换数据源零改动。
- **Rust 核心下沉**：日志解析器、配额适配器、数据模型、加解密全部放在共享 crate（`crates/core`）。当前只有 kimi 一路：parser `kimicode`（wire.jsonl）+ 配额适配器 `kimi.rs`（开放平台余额 + 非官方 coding usages best-effort）；增量游标/预聚合框架（`crates/core/logs/`）按平台泛化保留。桌面端 Tauri 命令是它的薄壳。TS 侧类型由 ts-rs 从 Rust 结构体生成，杜绝两边模型漂移。

├── packages/
│   ├── core-types/                 # TS 类型（ts-rs 生成，禁止手改）
│   └── ui/                         # 共享 Vue 组件（预留，基本为空）
├── docs/
│   ├── 01-需求文档.md
│   └── 02-开发计划.md
├── .github/workflows/              # CI：lint + test + tauri build
├── package.json                    # pnpm workspace 根
├── pnpm-workspace.yaml
└── Cargo.toml                      # Cargo workspace 根（members: apps/hub, crates/core, apps/desktop/src-tauri）

要点：

- 日志解析器与 HTTP 适配器只写一遍（Rust，`crates/core`），桌面端 Tauri 命令是薄壳——这是 monorepo 存在的核心理由。
- `packages/core-types` 由构建脚本跑 ts-rs 生成，CI 校验"生成结果与仓库一致"，防止手改。
- `packages/ui` 阶段一只放纯展示型小组件（如用量卡片、状态徽标），不强行抽。

## 3. 模块拆解

> 模块编号与《01-需求文档.md》一一对应。每个模块列出：前端页面/组件、Rust 侧命令、数据表要点、依赖的外部接口。

### Dashboard · 首页（跨模块摘要，非独立模块）

- `views/Dashboard.vue`：摘要卡片墙——今日 token 用量与缓存命中率（M1）、Kimi 配额/余额（M1）、当前代理模式与节点（M5）。
- 卡片按模块可用性渐进显示：某模块未配置或数据源不可达时，对应卡片显示"未配置"引导入口，不报错。
- 数据来自各模块 store 的缓存，Dashboard 自身不发起采集。

### M1 · AI 用量统计（只读；Kimi Code）

解析本机 kimi-code CLI 日志统一聚合 token 用量，配额/余额走 Kimi 适配器。**只读采集，不转发流量**。
**明确不支持**：Codex CLI 日志（使用频率极低）；GLM 套餐不列入。

**① 本地日志解析器（`crates/core/kimicode`）——实现要点**

- **kimi-code**：`~/.kimi-code/sessions/**/wire.jsonl`（目录可在 M6 设置中覆盖），每行一个事件 JSON；`usage.record` 事件（`usageScope: "turn"`，session 级快照须排除）含 `usage` 字段（`inputOther` / `output` / `inputCacheRead` / `inputCacheCreation`）与 `time`（Unix 毫秒）、`model`；同会话目录 `state.json` 提供 `cwd`，取末级目录名按项目分类。
- **增量解析**：`log_file` 游标表记录每个文件的读取偏移量，启动时与定时任务从上次位置续读；检测文件截断/轮换（当前 size < 记录 offset → 从头重扫该文件）。
- **逐行流式解析**，不把整个文件载入内存；单行解析失败跳过并计数（计入诊断日志），不中断整体扫描；`usage` 字段缺失按 0 处理。
- 事件归一化为 `UsageEvent { ts, platform, cli, session_id, project, model, input_other, output, cache_read, cache_creation, cost }` 写入事件表（`platform` + `cli` 两列区分来源，泛化保留）。其中 `cost` 可空：wire.jsonl 无此字段为 null，估算成本由单价表计算。
- **聚合维度**：按天 / 周 / 月 / 最近 5 小时；按项目 / 模型分组；缓存命中率 = `cache_read / (input_other + cache_read + cache_creation)`。预聚合写入日聚合表（同样带 `platform` + `cli`），页面查询只打聚合表，事件表仅用于回补与重算。
- **用量估值**：token 数 × 单价表得出估算金额；单价来源**待定**，先用 M6 中可配置的静态单价表（区分平台/模型、输入/输出/缓存）。

**② 配额 / 余额适配器（`crates/core/adapters/`）**

- **Kimi（`kimi.rs`）**：开放平台按量余额 `GET /v1/users/me/balance`；非官方 `GET /coding/v1/usages`（5h 滚动窗口 + 月度池余量），**best-effort**——接口可能失效，失败降级为"不可用"提示，不影响本地统计。

**前端页面/组件**

- `views/Usage.vue`：总览卡片墙（今日用量、配额/余额）+ 趋势图（ECharts 折线）+ 项目/模型分布
- `components/UsageTrendChart.vue`、`components/CacheHitBadge.vue`、`components/QuotaCard.vue`（配额/余额卡片，含"不可用/未配置"降级态）
- `stores/usage.ts`

**Rust 侧命令（Tauri commands）**

| 命令                                              | 作用                                                                                       |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `scan_usage_logs(platform?)`                      | 增量扫描（不传 platform 则全部；启动时与定时任务复用同一逻辑），返回 `ScanReport`（含坏行/失败文件计数） |
| `usage_summary(platform, range)`                  | 聚合总览（天/周/月/最近5小时），`platform='all'` 为跨平台合计                              |
| `usage_by_project` / `usage_by_model`（带 platform 参数） | 分组聚合（项目 / 模型）                                                              |
| `usage_series(platform, range)`                   | 时间序列（趋势图；Day 按小时、Week/Month 按日分桶）                                        |
| `quota_refresh(platform)` / `quota_latest(platform)` | 拉取平台配额并写快照 / 读最近快照                                                       |
| `platform_account_get` / `platform_account_set`   | 平台账户配置（凭据进 keyring）                                                             |

**数据表要点**

- `platform_account(id, platform, name, api_base, credential_ref, quota_total, quota_cycle, enabled)` — 平台账户；`credential_ref` 是 keyring 里的 key，不是凭据本身；`quota_total`/`quota_cycle` 为配额手录预留字段
- `log_file(id, platform, path, offset, size, mtime, last_scanned_at)` — 增量解析游标
- `usage_event(id, platform, cli, log_file_id, ts, session_id, project, model, input_other, output, cache_read, cache_creation, cost)` — 只追加；`cost` 可空；`log_file_id` 外键用于截断时整批重建
- `usage_daily(date, platform, cli, project, model, input_other, output, cache_read, cache_creation)` — 预聚合，`PRIMARY KEY(date, platform, cli, project, model)`，幂等重算
- `quota_snapshot(id, platform, total, used, remaining, detail_json, fetched_at)` — 配额/余额历史

**依赖外部接口**：本地文件系统（`~/.kimi-code`）、Kimi `/v1/users/me/balance` 与 `/coding/v1/usages`。

### M5 · 魔法工具

mihomo 以 Tauri sidecar 形式内置，软件通过其 RESTful API（默认 9090）驱动。阶段一只做核心三件套：**节点切换、系统代理开关、规则组切换**。

**前端页面/组件**

- `views/Proxy.vue`：代理组列表（当前选中节点、延迟着色）、规则组切换开关、系统代理开关、节点订阅卡
- `stores/proxy.ts`：轮询 mihomo API 保持状态同步（mihomo 侧才是事实源）
- `stores/subscription.ts`：订阅状态轮询与更新/导入触发

**Rust 侧命令**

| 命令                                                                  | 作用                                                            |
| --------------------------------------------------------------------- | --------------------------------------------------------------- |
| `proxy_status`                                                        | sidecar 存活 + mihomo `/proxies` 摘要                           |
| `select_proxy(group, node)`                                           | PUT `/proxies/{group}`                                          |
| `test_delay(group?)`                                                  | GET `/proxies/{name}/delay`，批量测速                           |
| `set_system_proxy(enabled)`                                           | 写系统代理（Windows 注册表，仅支持 Windows 见 NF-14）           |
| `switch_rule_mode(mode)`                                              | 规则组/模式切换（PATCH `/configs` 或按配置文件的策略组选择）    |
| `recover_system_proxy`                                                | 系统代理崩溃残留的自检恢复                                      |
| `subscription_status` / `subscription_set_url(url)` / `subscription_update` | 节点订阅状态 / 保存链接并立即更新 / 手动刷新（M5-07，另有 24h 定时循环） |
| `import_share_text(text)`                                             | 粘贴分享链接/yaml 导入节点（逐条容错记 failures）               |

**实现要点**

- `crates/core/mihomo/client.rs`：mihomo RESTful API 的薄封装。魔法工具是客户端本地功能，必须本地可用。
- sidecar 生命周期：Tauri 启动时拉起、退出时回收；端口冲突检测，9090 被占则顺延并写入设置。
- 分流规则（api.openai.com / anthropic.com 强制走稳定节点组）写在注入的 mihomo 配置模板里，软件只负责切换，不运行时改规则——改规则 = 换模板重载，降低复杂度。
- 节点导入（M5-07）：**订阅链接 + 定时更新为主**（用户当前为商家包月订阅用户；订阅更新失败保留旧节点并告警），手动粘贴分享链接（vless://、hysteria2:// 等）/yaml 片段为辅（后续境外 VPS 自建用）。
- 已知限制（已确认）：阶段一仅系统代理模式，**不做 TUN**——不读系统代理的终端 CLI 流量不经过 mihomo，AI 域名分流对其不生效；TUN 需管理员提权，后续按需评估。**M5 目标场景为软件与网站，不考虑游戏**。
- 系统代理开/关必须成对可靠：异常退出后下次启动检测"上次是否遗留开启状态"并提示恢复。

**数据表要点**

- `proxy_setting(key, value)`：当前模式、选中的节点、系统代理状态、订阅地址
- 节点信息不落库，每次从 mihomo API 现取

**依赖外部接口**：mihomo RESTful API (9090)、系统代理设置接口。

### M6 · 设置

各模块配置的统一入口 + 通用偏好。

**前端页面/组件**

- `views/Settings.vue`：分区页——AI 用量（Kimi key、api_base、日志目录覆盖）、魔法工具（订阅地址）、通用偏好（主题亮暗/跟随系统）
- `stores/settings.ts`：通用偏好（主题、Kimi 日志目录覆盖）以 localStorage 落盘

**说明**

- Kimi 账户配置（key / api_base）走 M1 的 `platform_account_get` / `platform_account_set` 命令，凭据进 keyring。
- 通用偏好当前无独立设置命令，由前端 store 持久化（localStorage），后续可迁移到 SQLite。

## 4. MVP 定义与里程碑

### 阶段一（不依赖新硬件）：脚手架 + M1 AI 用量统计 + M5 核心三件套 + M6 基础

| 里程碑             | 内容                                                                                                                                   | 验收标准                                                                                                                                                                                                 | 状态 |

## 5. 开发规范

- **提交信息**：Conventional Commits —— `feat(usage): add wire.jsonl incremental parser`、`fix(proxy): restore system proxy on exit`。scope 用模块小写名（usage/proxy/settings/hub/core）。
- **分支策略**：个人项目走 trunk-based：直接在 `master` 上小步提交，较大的功能用 `feat/xxx` 短生命周期分支 + 自审 PR（为了跑 CI 和留记录）。tag 即发布。
- **代码风格**：
  - Rust：`rustfmt` + `clippy`（CI 中 `-D warnings`）。
  - TS/Vue：ESLint 9 flat config（`@vue/eslint-config-typescript`）+ Prettier（ESLint 只管规则、Prettier 只管格式，职责分开）。
  - 提交前钩子（已确认，**从简**）：simple-git-hooks + lint-staged，只对本次暂存的文件跑 prettier + eslint --fix，不做全仓检查；全仓检查由 CI 兜底。
- **类型纪律**：`packages/core-types` 只由 ts-rs 生成；前端 invoke 的参数/返回类型必须来自该包。
