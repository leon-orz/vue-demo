> 本文档面向实际开工：技术选型、仓库结构、模块拆解、里程碑、规范与测试。
> 配套文档：《docs/01-需求文档.md》（模块编号 M1~M6 与其对齐）、《docs/03-部署文档.md》。

## 1. 技术选型与理由

### 1.1 总览

| 层 | 选型 | 说明 |
|---|---|---|
| 桌面壳 | Tauri 2 | 安装包小、内存占用低，Rust 侧可直接写系统能力与网络采集，sidecar 机制适合内嵌 mihomo 内核 |
| 前端框架 | Vue 3 + TypeScript + Vite 8 | Tauri 官方脚手架一等支持；`<script setup>` + Composition API；Vite 用最新稳定版 8.x（Rolldown 内核），详见 1.4 |
| 状态管理 | Pinia | Vue 3 官方推荐，TS 类型友好 |
| 组件与样式 | **shadcn-vue + Tailwind CSS** | 不使用成品 UI 库，见 1.2 |
| 本地存储 | SQLite（tauri-plugin-sql） | 配置与用量缓存；migration 用插件自带机制管理 |
| 密钥存储 | **keyring-rs（倾向）** | 见 1.3 对比 |
| 图表 | ECharts | 仪表盘、用量趋势；按需引入控制包体积 |
| 后端/中枢 | Rust（axum + tokio + sqlx） | 与桌面端共享同一份数据模型和平台适配器 crate，避免双语言重复实现 |
| 代理内核 | mihomo sidecar | 随安装包分发，RESTful API（默认 9090）驱动 |
| 包管理 | pnpm workspace + Cargo workspace | monorepo 双 workspace，见第 2 节 |

### 1.2 组件方案：shadcn-vue vs 纯 UnoCSS 手写

已确认：**不使用成品 UI 组件库**（Naive UI / Element Plus 均排除）。两个候选：

| 维度 | shadcn-vue（选定） | 纯 UnoCSS 手写组件 |
|---|---|---|
| 本质 | 组件以**源码形式**拷进仓库（基于 Reka UI 无头组件 + Tailwind），归项目所有 | 只有原子化 CSS 引擎，组件全部从零写 |
| 现成度 | Button/Dialog/Select/Table/Tooltip 等开箱可用，可随意改 | 每个组件自己造，工作量大 |
| 可访问性 | Reka UI 处理焦点管理、键盘导航等 | 自己处理，容易留坑 |
| 暗色模式 | Tailwind `dark:` 变体，主题定制极方便 | 同样方便，但组件样式要自己设计 |
| 依赖负担 | 无运行时库依赖，代码就在仓库里 | 最轻，但时间成本高 |

**结论：shadcn-vue + Tailwind CSS**。它不是传统意义上的"UI 库依赖"，而是一套拷进仓库的组件源码，既满足"不用 UI 库"的诉求，又不用从零造 Dialog/Select 这类容易出可访问性问题的组件；暗色模式用 Tailwind `dark:` 即可。**注意：shadcn-vue 依赖 Tailwind，因此不混用 UnoCSS**。图表仍用 ECharts 按需引入。

### 1.3 密钥存储：keyring-rs（已定）

S1-1 已用 keyring-rs 落地：直译"敏感 key 存系统钥匙串"的需求，桌面端走 Windows 凭据管理器（**注意：keyring 3 默认不启用任何平台后端，需显式 `features = ["windows-native"]`**，否则会静默退化为 mock 内存存储——S1-1 实测踩过此坑）；hub 侧（Linux 无桌面环境）封装同一 trait，底层退回"主密钥加密的文件存储"，接口不变。备选 stronghold（加密快照文件）因引入额外概念已排除。

### 1.4 基础环境与版本清单（已确认）

| 项 | 版本/方案 | 说明 |
|---|---|---|
| Node.js | **24 LTS** | active LTS，生命周期长；Tauri 2 要求 ≥ 20.18 |
| pnpm | 最新稳定版，corepack 管理 | `package.json` 写 `packageManager` 字段锁死版本 |
| Rust | stable 最新（rustup 管理） | 已安装 1.98.1；crates.io 走 rsproxy 国内镜像（`~/.cargo/config.toml`） |
| Vite | **8.x 最新稳定** | Rolldown 内核；Tauri 适配：固定 dev 端口 1420、`clearScreen: false`、`build.target` 对齐 Windows WebView2 Chromium；ECharts 等大包手动分包 |
| Tauri | 2.x 最新稳定 | `tauri build` 出 Windows NSIS 安装包，mihomo sidecar 随包分发（仅 Windows 二进制） |
| TypeScript | strict 全开 | 前后端共享类型由 ts-rs 生成，invoke 参数/返回类型禁止手写 |
| 版本锁定 | lockfile 锁定（Cargo.lock + pnpm-lock.yaml 提交入库） | 两台开发机与 CI 装出一致结果 |
| 编辑器 | 仓库内置 `.editorconfig` + VSCode 推荐配置 | 换电脑开箱即用 |

### 1.5 关键架构原则

- **不自研通用后端**：所有外部依赖（new-api、mihomo、SSH/Docker、Netdata）都是现成服务，软件只做客户端与胶水层。
- **数据获取层可替换**：定义 `DataSource` trait（Rust）与对应的 TS 接口，实现 `DirectSource`（客户端本地采集）与 `HubSource`（从中枢拉取）。阶段一只有 DirectSource，阶段二加 HubSource，UI 层零改动。
- **Rust 核心下沉**：日志解析器、平台适配器、数据模型、加解密全部放在共享 crate（`crates/core`），桌面端 Tauri 命令和 hub HTTP 接口都是它的薄壳。TS 侧类型由 ts-rs 从 Rust 结构体生成，杜绝两边模型漂移。

```
│   │   ├── src-tauri/

│   │   │   │   └── main.rs

│   │   │   └── tauri.conf.json
│   │   └── package.json
│   └── hub/                        # 中枢服务（纯 Rust，无界面）
│       ├── src/
│       │   ├── api/                # axum 路由：/usage /config /control
│       │   ├── collector/          # 定时采集任务（调 crates/core 适配器）
│       │   ├── store/              # SQLite 持久化
│       │   └── main.rs
│       └── Cargo.toml
├── crates/
│   └── core/                       # 共享 Rust crate
│       ├── src/
│       │   ├── models/             # 数据模型（serde + ts-rs 导出）
│       │   ├── kimicode/           # Kimi Code 本地日志解析与聚合（wire.jsonl）
│       │   ├── adapters/           # HTTP 适配器：kimi.rs（开放平台余额）/ newapi_admin.rs（网关）
│       │   ├── datasource/         # DataSource trait + Direct/Hub 实现
│       │   ├── keystore/           # 密钥存储抽象（keyring / 加密文件）
│       │   └── mihomo/             # mihomo RESTful API 客户端
│       └── Cargo.toml
├── packages/
│   ├── core-types/                 # TS 类型（ts-rs 生成，禁止手改）
│   └── ui/                         # 共享 Vue 组件（阶段一基本为空，为远期多端预留）
├── docs/
│   ├── 01-需求文档.md
│   ├── 02-开发计划.md
│   └── 03-部署文档.md
├── .github/workflows/              # CI：lint + test + tauri build
├── package.json                    # pnpm workspace 根
├── pnpm-workspace.yaml
└── Cargo.toml                      # Cargo workspace 根（members: apps/hub, crates/core, apps/desktop/src-tauri）
```

要点：

- 日志解析器与 HTTP 适配器只写一遍（Rust，`crates/core`），桌面端和 hub 共用——这是 monorepo 存在的核心理由。
- `packages/core-types` 由构建脚本跑 ts-rs 生成，CI 校验"生成结果与仓库一致"，防止手改。
- `packages/ui` 阶段一只放纯展示型小组件（如用量卡片、状态徽标），不强行抽。

## 3. 模块拆解（M1~M6 + Dashboard）

> 模块编号与《01-需求文档.md》一一对应。每个模块列出：前端页面/组件、Rust 侧命令、数据表要点、依赖的外部接口。

### Dashboard · 首页（跨模块摘要，非独立模块）

- `views/Dashboard.vue`：摘要卡片墙——今日 Kimi token 用量与缓存命中率（M1）、Kimi 账户余额（M1）、网关余额/状态（M2，阶段二）、服务器在线与负载（M3，阶段二）、NAS 存储占用（M4，阶段二）、当前代理模式与节点（M5）。
- 卡片按模块可用性渐进显示：某模块未配置或数据源不可达时，对应卡片显示"未配置"引导入口，不报错。
- 数据来自各模块 store 的缓存，Dashboard 自身不发起采集。

### M1 · Kimi 统计

两部分：① Kimi Code 包月本地日志统计（核心，纯本地、无网络依赖）；② Kimi 开放平台 API 余额。
**明确不做**：Kimi Code 限额余量抓取。

**① 本地日志解析器（`crates/core/kimicode`）——实现要点**

- 数据源：`~/.kimi-code/sessions/**/wire.jsonl`（目录可在 M6 设置中覆盖），每行一个事件 JSON；`usage.record` 事件（`usageScope: "turn"`，session 级快照须排除）含 `usage` 字段（`inputOther` / `output` / `inputCacheRead` / `inputCacheCreation`）与 `time`（Unix 毫秒）、`model`；同会话目录 `state.json` 提供 `cwd`，取末级目录名按项目分类。
- **增量解析**：用 `kimi_log_file` 表记录每个文件的读取偏移量，启动时与定时任务从上次 offset 续读，不做全量重扫；检测文件截断/轮换（当前 size < 记录 offset → 从头重扫该文件）。
- **逐行流式解析**，不把整个文件载入内存；单行解析失败跳过并计数（计入诊断日志），不中断整体扫描；`usage` 字段缺失按 0 处理。
- 事件归一化为 `KimiUsageEvent { ts, session_id, project, model, input_other, output, cache_read, cache_creation }` 写入事件表（`project` 取自 `state.json` 的 `cwd`，取末级目录名展示）。
- **聚合维度**：按天 / 周 / 月 / 最近 5 小时；按项目 / 按模型分组；缓存命中率 = `cache_read / (input_other + cache_read + cache_creation)`。预聚合写入 `kimi_usage_daily`，页面查询只打聚合表，事件表仅用于回补与重算。
- **用量估值**：token 数 × 单价表得出估算金额；单价来源**待定**，先用 M6 中可配置的静态单价表（区分输入/输出/缓存）。

**② Kimi 开放平台余额（`crates/core/adapters/kimi.rs`）**

- 接口：`GET https://api.moonshot.cn/v1/users/me/balance`，`Authorization: Bearer {api_key}`。
- 字段：`available_balance` / `voucher_balance` / `cash_balance`，单位人民币元。
- 凭据只进 keyring，数据库仅存引用。

**前端页面/组件**

- `views/Kimi.vue`：今日/本周/本月用量卡片 + 最近 5 小时用量条 + 趋势图（ECharts 折线）+ 项目/模型分布（饼图或条形图）+ 开放平台余额卡片
- `components/UsageTrendChart.vue`、`components/CacheHitBadge.vue`
- `stores/kimi.ts`

**Rust 侧命令（Tauri commands）**

| 命令 | 作用 |
|---|---|
| `scan_kimi_logs` | 增量扫描（启动时与定时任务复用同一逻辑），返回 `KimiScanReport`（含坏行/失败文件计数） |
| `kimi_usage_summary(range)` | 聚合总览（天/周/月/最近5小时） |
| `kimi_usage_by_project` / `kimi_usage_by_model` | 分组聚合（项目 / 模型） |
| `kimi_usage_series(range)` | 时间序列（趋势图；Day 按小时、Week/Month 按日分桶） |
| `kimi_balance_refresh` / `kimi_balance_latest` | 拉取开放平台余额并写快照 / 读最近快照 |
| `kimi_account_get` / `kimi_account_set` | 开放平台账户配置（凭据进 keyring） |

**数据表要点**

- `kimi_account(id, name, api_base, credential_ref, enabled)` — `credential_ref` 是 keyring 里的 key，不是凭据本身
- `kimi_log_file(id, path, offset, size, mtime, last_scanned_at)` — 增量解析游标
- `kimi_usage_event(id, log_file_id, ts, session_id, project, model, input_other, output, cache_read, cache_creation)` — 只追加；`log_file_id` 外键用于截断时整批重建
- `kimi_usage_daily(date, project, model, input_other, output, cache_read, cache_creation)` — 预聚合，`PRIMARY KEY(date, project, model)`，幂等重算
- `kimi_balance_snapshot(id, available, voucher, cash, fetched_at)` — 余额历史

**依赖外部接口**：本地文件系统（`~/.kimi-code`）、Kimi 开放平台 `/v1/users/me/balance`。

### M2 · 我的 API 平台（自建 new-api 网关，只读）

阶段二。网关本身的部署见《03-部署文档.md》，软件侧只做**只读接入与展示**，管理一律跳 new-api 自带 Web 管理台。

**前端页面/组件**

- `views/Gateway.vue`：网关连接状态、余额、按 key / 按模型的用量表格、渠道健康只读列表
- `components/GatewaySetup.vue`：网关地址 + 凭据配置（属 M6 设置的一部分，此处为快捷入口）
- `stores/gateway.ts`

**Rust 侧命令**

| 命令 | 作用 |
|---|---|
| `gateway_status` | 探活 + 版本信息 |
| `gateway_usage(range, group_by)` | 拉取消耗日志并按 key/模型/时间段聚合 |
| `gateway_channels` | 渠道列表与健康状态（只读） |

**适配器要点（`crates/core/adapters/newapi_admin.rs`）**

- `GET {gateway}/api/user/self`：网关账户余额（quota 换算同 new-api 约定，$1 = 500,000 quota）。
- `GET {gateway}/api/log/self`：消费日志，客户端分页拉取后按 key、按模型、按时间段聚合。
- 渠道健康：走 new-api 渠道管理 API 的只读端点，所需令牌权限范围接入时确认（**待定**）。
- 渠道/令牌的增删改不做，UI 提供"打开管理台"按钮。

**数据表要点**

- 余额复用快照思路：`gateway_balance_snapshot(id, quota, used_quota, fetched_at)`
- 聚合缓存 `gateway_usage_cache(id, period, key_name, model, tokens, cost, fetched_at)`（缓存策略**待定**，先用短 TTL 内存缓存）

**依赖外部接口**：new-api `/api/user/self`、`/api/log/self`、渠道只读端点。

### M3 · 服务器

阶段二。一体机（Debian 12 + Docker）的监控与基础控制。

**前端页面/组件**

- `views/Server.vue`：主机状态卡片（CPU/内存/磁盘/温度，来自 Netdata）
- `components/ContainerList.vue`：Docker 容器列表 + 启动/停止/重启
- `components/PowerButtons.vue`：WOL 开机、SSH 关机 + 最近状态
- `stores/server.ts`

**Rust 侧命令**

| 命令 | 作用 |
|---|---|
| `server_overview(host_id)` | 调 Netdata API 取摘要指标 |
| `list_containers(host_id)` / `container_action(id, op)` | Docker 容器查询与操作（SSH 隧道内走 Docker socket） |
| `wake_host(host_id)` | 发送 WOL 魔法包 |
| `shutdown_host(host_id)` | SSH 执行关机（`systemctl poweroff`），二次确认 |
| `test_ssh(host_id)` | 连通性自检（配置向导用） |

**实现要点**

- SSH：Rust 侧 `russh`；Docker 操作走 SSH 本地转发 + Docker socket（`bollard`），不开 TCP 2375。
- 监控：直接读 Netdata REST API（`/api/v1/info`、`/api/v1/data`），不自建采集。
- WOL：UDP 魔法包，注意 Tailscale 组网与局域网广播的关系——WOL 通常需在同网段或网关转发，**跨网段唤醒方案待定**。

**数据表要点**

- `host(id, name, tailscale_ip, ssh_port, ssh_credential_ref, wol_mac, netdata_port, enabled)` — M3/M4 共用同一条主机记录

**依赖外部接口**：SSH (22)、Docker socket、Netdata (19999)、WOL (UDP 9)。

### M4 · NAS

与 M3 完全独立的模块（M3 管"机器"，M4 管"存储服务"）。NAS 形态未定死，按插件化设计：先定义 `NASProvider` trait，阶段二给默认实现，阶段三做深度功能。

**前端页面/组件**

- `views/Nas.vue`：存储池/分区占用（容量条）、磁盘 SMART 健康列表、备份状态卡片
- `stores/nas.ts`

**Rust 侧命令**

| 命令 | 作用 |
|---|---|
| `nas_storage(host_id)` | 各挂载点容量/占用（默认实现：SSH 执行 `df` 解析） |
| `nas_smart(host_id)` | 磁盘 SMART 摘要（默认实现：SSH 执行 `smartctl` 解析） |
| `nas_backup_status(host_id)` | 备份状态（阶段三；先手动登记最近冷备时间） |

**实现要点**

- `NASProvider` trait：`storage()` / `smart()` / `shares()` / `backup_status()`，阶段二默认实现 = SSH 命令采集（Debian 宿主机直采）；以后若上 TrueNAS 等成品系统，新增 Provider 实现即可，UI 不变。
- 阶段三深度：共享管理（SMB/NFS 增删改）、SMART 明细与告警、备份状态自动检测。

**数据表要点**

- 复用 `host` 表；新增 `backup_record(id, host_id, target, last_backup_at, note)`（阶段三扩展自动检测字段）

**依赖外部接口**：SSH（`df` / `smartctl`）。

### M5 · 魔法工具

mihomo 以 Tauri sidecar 形式内置，软件通过其 RESTful API（默认 9090）驱动。阶段一只做核心三件套：**节点切换、系统代理开关、规则组切换**。

**前端页面/组件**

- `views/Proxy.vue`：代理组列表（当前选中节点、延迟着色）、规则组切换开关、系统代理开关
- `components/NodeCard.vue`：节点名 + 延迟 + 测速按钮
- `stores/proxy.ts`：轮询 mihomo API 保持状态同步（mihomo 侧才是事实源）

**Rust 侧命令**

| 命令 | 作用 |
|---|---|
| `proxy_status` | sidecar 存活 + mihomo `/proxies` 摘要 |
| `select_proxy(group, node)` | PUT `/proxies/{group}` |
| `test_delay(group?)` | GET `/proxies/{name}/delay`，批量测速 |
| `set_system_proxy(enabled)` | 写系统代理（Windows 注册表，仅支持 Windows 见 NF-14） |
| `switch_rule_mode(mode)` | 规则组/模式切换（PATCH `/configs` 或按配置文件的策略组选择） |

**实现要点**

- `crates/core/mihomo/client.rs`：mihomo RESTful API 的薄封装，hub 不需要此模块（魔法工具是客户端本地功能，中枢不可达时也必须可用）。
- sidecar 生命周期：Tauri 启动时拉起、退出时回收；端口冲突检测，9090 被占则顺延并写入设置。
- 分流规则（api.openai.com / anthropic.com 强制走稳定节点组）写在注入的 mihomo 配置模板里，软件只负责切换，不运行时改规则——改规则 = 换模板重载，降低复杂度。
- 系统代理开/关必须成对可靠：异常退出后下次启动检测"上次是否遗留开启状态"并提示恢复。

**数据表要点**

- `proxy_setting(key, value)`：当前模式、选中的节点、系统代理状态、订阅地址
- 节点信息不落库，每次从 mihomo API 现取

**依赖外部接口**：mihomo RESTful API (9090)、系统代理设置接口。

### M6 · 设置

各模块配置的统一入口 + 中枢连接与数据源模式 + 通用偏好。

**前端页面/组件**

- `views/Settings.vue`：分区页——Kimi（开放平台 key、日志目录覆盖）、我的 API 平台（网关地址与凭据）、服务器/NAS（主机列表 CRUD）、魔法工具（订阅地址、模板选择、端口）、中枢连接、通用偏好
- `components/DatasourceBadge.vue`：全局数据源模式指示（直连/中枢/降级）
- `stores/settings.ts`

**Rust 侧命令**

| 命令 | 作用 |
|---|---|
| `get_settings` / `set_setting(key, value)` | 通用偏好读写（主题、刷新频率、开机自启、日志级别） |
| `set_datasource(mode)` | 切换 Direct / Hub 数据源（写入设置表，Dashboard 与各模块据此切换） |
| `hub_status` | 中枢连通性探测 + 当前模式 |

**中枢（hub）——架构能力，非独立功能模块**

hub 是同一 monorepo 的另一 Rust 编译产物（`apps/hub`），跑在一体机上，无界面，仅监听 Tailscale 网卡。职责：统一对外采集（Kimi 余额、网关数据）、集中存历史、加密存配置并下发、转发控制指令（如 SSH 重启容器）。客户端侧体现为 `DataSource` 的 `HubSource` 实现（`crates/core/datasource/hub.rs`）：

- 离线降级：hub 连续 N 次不可达自动切回 `DirectSource`，`DatasourceBadge` 显示当前模式；M5 魔法工具不走 hub，天然不受影响。
- 配置同步：客户端启动时拉 hub 配置比对版本，冲突策略**待定**（先按"hub 为准"）。
- 本地日志统计（M1 的 wire.jsonl 解析）始终在各客户端本地执行，hub 只汇聚余额类数据；日志数据是否上报 hub 属阶段三增强，**待定**。
- hub 存储：SQLite 起步；是否升级 Postgres **待定**（单用户量级预计不需要）。

**数据表要点**

- `setting(key, value)` — 通用偏好与数据源模式
- hub 侧：`client_config(id, scope, payload_encrypted, version, updated_at)`

**依赖外部接口**：Tailscale 网络（详见《03-部署文档.md》）。

## 5. 开发规范

- **提交信息**：Conventional Commits —— `feat(kimi): add wire.jsonl incremental parser`、`fix(proxy): restore system proxy on exit`。scope 用模块小写名（kimi/gateway/server/nas/proxy/settings/hub/core）。
- **分支策略**：个人项目走 trunk-based：直接在 `main` 上小步提交，较大的功能用 `feat/xxx` 短生命周期分支 + 自审 PR（为了跑 CI 和留记录）。tag 即发布。
- **代码风格**：
  - Rust：`rustfmt` + `clippy`（CI 中 `-D warnings`）。
  - TS/Vue：ESLint 9 flat config（`@vue/eslint-config-typescript`）+ Prettier（ESLint 只管规则、Prettier 只管格式，职责分开）。
  - 提交前钩子（已确认，**从简**）：simple-git-hooks + lint-staged，只对本次暂存的文件跑 prettier + eslint --fix，不做全仓检查；全仓检查由 CI 兜底。
- **类型纪律**：`packages/core-types` 只由 ts-rs 生成；前端 invoke 的参数/返回类型必须来自该包。

## 6. 测试策略

| 层 | 策略 | 工具 |

| 日志解析器（重点） | **fixture 驱动单元测试**：脱敏的 wire.jsonl 样本（正常事件、缺 usage 事件、损坏行、空行、多会话多项目）锁定解析行为；专项用例覆盖增量偏移（续读、文件截断后重扫、新增文件发现）与聚合正确性（缓存命中率公式、天/周/月/最近5小时边界） | cargo test + fixture |

| Rust 其他逻辑 | 数据源切换、离线降级、WOL 包构造、SSH 命令输出解析（df/smartctl 用录制输出 fixture） | cargo test |
| 前端组件/Store | 关键 store（kimi/proxy/settings）单测，组件测试从简 | Vitest |

## 7. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| wire.jsonl 是 Kimi Code 内部格式，未文档化，版本升级可能变更字段 | M1 统计失效或算错 | 解析器容错设计（未知字段忽略、单行失败不中断）；fixture 测试锁定当前行为，升级后跑测试即知是否破坏；解析失败时 Kimi 页降级提示，不影响余额等其他功能 |
| 日志体积随使用增长，事件表膨胀 | 扫描变慢、SQLite 变大 | 增量解析避免重扫；预聚合后事件表可按月归档清理（阶段三打磨项）；最近 5 小时窗口走事件表索引查询 |
| mihomo 内核打包进 Tauri sidecar | 安装包体积增大、杀软误报 | 已确认**仅支持 Windows**（NF-14），只打包 Windows 版 mihomo 二进制，macOS 签名/公证问题不存在；选 mihomo 官方 release 固定版本，升级走配置 |
| 二手硬件 / 一体机到货延期 | 阶段二无法启动 | 阶段一完全不依赖新硬件；hub 可先在笔记本上 Docker 里跑通开发联调，硬件只影响正式部署 |
| new-api 网关日志接口数据量大 | M2 拉取慢、本地缓存膨胀 | 按时间段分页拉取 + 本地聚合缓存；超出预期的数据量时再评估 hub 侧预聚合 |
| NAS 形态未定 | M4 设计悬空 | `NASProvider` trait 隔离，阶段二只做 SSH 直采默认实现（存储占用 + SMART），换方案只换 Provider |
| 系统代理状态残留（软件崩溃后系统代理还开着） | 用户断网、体验事故 | M5 启动自检 + 退出钩子双重保障；写死恢复路径的测试用例 |
| Tailscale 网络异常导致 hub 不可达 | 中枢数据源中断 | 离线降级是设计内行为（见 M6 节），不是异常兜底 |
