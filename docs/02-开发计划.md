## 1. 技术选型与理由

### 1.1 总览

| 层 | 选型 | 说明 |
|---|---|---|
| 桌面壳 | Tauri 2 | 安装包小、内存占用低，Rust 侧可直接写系统能力与网络采集，sidecar 机制适合内嵌 mihomo 内核 |
| 前端框架 | Vue 3 + TypeScript + Vite 8 | Tauri 官方脚手架一等支持；`<script setup>` + Composition API；Vite 用最新稳定版 8.x（Rolldown 内核），详见 1.4 |
| 状态管理 | Pinia | Vue 3 官方推荐，TS 类型友好 |
| 组件与样式 | **shadcn-vue + Tailwind CSS** | 不使用成品 UI 库，见 1.2 |
| 本地存储 | SQLite（sqlx，Rust 侧独占） | 配置与用量缓存；schema 收归 `crates/core/migrations/`，由 Rust 按版本号迁移执行（tauri-plugin-sql 已移除，前端不直连数据库） |
| 密钥存储 | **keyring-rs（倾向）** | 见 1.3 对比 |
| 图表 | ECharts | 仪表盘、用量趋势；按需引入控制包体积 |
| 后端/中枢 | Rust（axum + tokio + sqlx） | 与桌面端共享同一份数据模型和平台适配器 crate，避免双语言重复实现 |
| 代理内核 | mihomo sidecar | 随安装包分发，RESTful API（默认 9090）驱动 |
| 包管理 | pnpm workspace + Cargo workspace | monorepo 双 workspace，见第 2 节 |

### 1.2 组件方案：shadcn-vue vs 纯 UnoCSS 手写

已确认：**不使用成品 UI 组件库**（Naive UI / Element Plus 均排除）。两个候选：

| 维度 | shadcn-vue（选定） | 纯 UnoCSS 手写组件 |
|---|---|---|
| 本质 | 组件以**源码形式**拷进仓库（基于 Reka UI 无头组件 + Tailwind），归项目所有 | 只有原子化 CSS 引擎，组件全部从零写 |
| 现成度 | Button/Dialog/Select/Table/Tooltip 等开箱可用，可随意改 | 每个组件自己造，工作量大 |
| 可访问性 | Reka UI 处理焦点管理、键盘导航等 | 自己处理，容易留坑 |
| 暗色模式 | Tailwind `dark:` 变体，主题定制极方便 | 同样方便，但组件样式要自己设计 |
| 依赖负担 | 无运行时库依赖，代码就在仓库里 | 最轻，但时间成本高 |

**结论：shadcn-vue + Tailwind CSS**。它不是传统意义上的"UI 库依赖"，而是一套拷进仓库的组件源码，既满足"不用 UI 库"的诉求，又不用从零造 Dialog/Select 这类容易出可访问性问题的组件；暗色模式用 Tailwind `dark:` 即可。**注意：shadcn-vue 依赖 Tailwind，因此不混用 UnoCSS**。图表仍用 ECharts 按需引入。

### 1.3 密钥存储：keyring-rs（已定）

S1-1 已用 keyring-rs 落地：直译"敏感 key 存系统钥匙串"的需求，桌面端走 Windows 凭据管理器（**注意：keyring 3 默认不启用任何平台后端，需显式 `features = ["windows-native"]`**，否则会静默退化为 mock 内存存储——S1-1 实测踩过此坑）；hub 侧（Linux 无桌面环境）封装同一 trait，底层退回"主密钥加密的文件存储"，接口不变。备选 stronghold（加密快照文件）因引入额外概念已排除。

### 1.4 基础环境与版本清单（已确认）

| 项 | 版本/方案 | 说明 |
|---|---|---|
| Node.js | **24 LTS** | active LTS，生命周期长；Tauri 2 要求 ≥ 20.18 |
| pnpm | 最新稳定版，corepack 管理 | `package.json` 写 `packageManager` 字段锁死版本 |
| Rust | stable 最新（rustup 管理） | 已安装 1.98.1；crates.io 走 rsproxy 国内镜像（`~/.cargo/config.toml`） |
| Vite | **8.x 最新稳定** | Rolldown 内核；Tauri 适配：固定 dev 端口 1420、`clearScreen: false`、`build.target` 对齐 Windows WebView2 Chromium；ECharts 等大包手动分包 |
| Tauri | 2.x 最新稳定 | `tauri build` 出 Windows NSIS 安装包，mihomo sidecar 随包分发（仅 Windows 二进制） |
| TypeScript | strict 全开 | 前后端共享类型由 ts-rs 生成，invoke 参数/返回类型禁止手写 |
| 版本锁定 | lockfile 锁定（Cargo.lock + pnpm-lock.yaml 提交入库） | 两台开发机与 CI 装出一致结果 |
| 编辑器 | 仓库内置 `.editorconfig` + VSCode 推荐配置 | 换电脑开箱即用 |

### 1.5 关键架构原则

- **不自建 API 中转网关**（已决策）：原「自建 new-api 网关」方案取消，AI 用量采集全部走「本地 CLI 日志解析 + 平台 API 直连」两条路，软件只读不转发流量。其余外部依赖（mihomo、SSH/Docker、Netdata）都是现成服务，软件只做客户端与胶水层。
- **数据获取层可替换**：定义 `DataSource` trait（Rust）与对应的 TS 接口，实现 `DirectSource`（客户端本地采集）与 `HubSource`（从中枢拉取）。阶段一只有 DirectSource，阶段二加 HubSource，UI 层零改动。
- **Rust 核心下沉**：日志解析器、配额适配器、数据模型、加解密全部放在共享 crate（`crates/core`）。日志侧三个 parser：`kimicode`（wire.jsonl）、`mimocode`（MiMo 本地 SQLite 只读）、`omp`（oh-my-pi JSONL，复用 kimicode 的增量游标/预聚合框架）；配额侧三个适配器：Kimi（非官方 best-effort）、DeepSeek（官方余额 API）、MiMo（手录总额 + 本地推算，无网络请求）。桌面端 Tauri 命令和 hub HTTP 接口都是薄壳。TS 侧类型由 ts-rs 从 Rust 结构体生成，杜绝两边模型漂移。

要点：

- 日志解析器与 HTTP 适配器只写一遍（Rust，`crates/core`），桌面端和 hub 共用——这是 monorepo 存在的核心理由。

- `packages/ui` 阶段一只放纯展示型小组件（如用量卡片、状态徽标），不强行抽。

## 3. 模块拆解（M1~M6 + Dashboard）

> 模块编号与《01-需求文档.md》一一对应。每个模块列出：前端页面/组件、Rust 侧命令、数据表要点、依赖的外部接口。

### Dashboard · 首页（跨模块摘要，非独立模块）

- `views/Dashboard.vue`：摘要卡片墙——今日各平台 token 用量与缓存命中率（M1）、各平台配额/余额（M1）、服务器在线与负载（M3，阶段二）、NAS 存储占用（M4，阶段二）、当前代理模式与节点（M5）。
- 卡片按模块可用性渐进显示：某模块未配置或数据源不可达时，对应卡片显示"未配置"引导入口，不报错。
- 数据来自各模块 store 的缓存，Dashboard 自身不发起采集。

### M1 · AI 用量统计（多平台聚合，只读）

多平台用量聚合：解析本机三类 CLI 日志统一聚合 token 用量，配额/余额分平台适配。**只读采集，不转发流量**（自建 API 中转网关方案已取消，原 M2 需求并入本模块）。
**明确不支持**：Codex CLI 日志（使用频率极低）；GLM 套餐不列入；dsh（DeepSeek Harness）为阶段三预留。

**① 本地日志解析器（`crates/core/kimicode` + `mimocode` + `omp`）——实现要点**

三个平台三种日志来源，parser 各自实现、归一化为统一事件模型后走同一套增量游标与预聚合框架：

- **kimi-code**：`~/.kimi-code/sessions/**/wire.jsonl`（目录可在 M6 设置中覆盖），每行一个事件 JSON；`usage.record` 事件（`usageScope: "turn"`，session 级快照须排除）含 `usage` 字段（`inputOther` / `output` / `inputCacheRead` / `inputCacheCreation`）与 `time`（Unix 毫秒）、`model`；同会话目录 `state.json` 提供 `cwd`，取末级目录名按项目分类。
- **MiMo Code（`crates/core/mimocode`）**：`~/.local/share/mimocode/mimocode.db`，SQLite **只读打开**（`mode=ro`，不写 WAL/不加锁）；`message` 表 `data` 字段为 JSON，含 tokens / cost / modelID / providerID。增量以行 id 或时间戳为游标。
- **oh-my-pi（`crates/core/omp`）**：`~/.omp/agent/sessions/**/*.jsonl`，assistant 行带 `usage{input, output, cacheRead, cacheWrite}` + provider / model + timestamp，异常行（如 `stopReason` 为错误）单列计数。复用 kimicode 的增量游标 / 预聚合框架，只换行解析逻辑。
- **增量解析**：`log_file` 游标表记录每个文件的读取偏移量（mimocode 为行游标），启动时与定时任务从上次位置续读；检测文件截断/轮换（当前 size < 记录 offset → 从头重扫该文件）。
- **逐行流式解析**，不把整个文件载入内存；单行解析失败跳过并计数（计入诊断日志），不中断整体扫描；`usage` 字段缺失按 0 处理。
- 事件归一化为 `UsageEvent { ts, platform, cli, session_id, project, model, input_other, output, cache_read, cache_creation, cost }` 写入事件表（新增 `platform` + `cli` 两列区分来源，新 migration 对既有 kimi 数据回填 `platform='kimi', cli='kimi-code'`）。其中 `cost` 可空：mimocode / omp 日志自带成本字段时保留（MiMo 套餐进度推算依赖它），wire.jsonl 无此字段则为 null，估算成本仍由单价表计算。
- **聚合维度**：按天 / 周 / 月 / 最近 5 小时；按平台 / 项目 / 模型分组；缓存命中率 = `cache_read / (input_other + cache_read + cache_creation)`。预聚合写入日聚合表（同样带 `platform` + `cli`），页面查询只打聚合表，事件表仅用于回补与重算。
- **指标策略 best-effort**：取消网关后失去跨平台耗时/错误率对比手段，日志里有什么看什么（如 omp 的 `stopReason` 错误计数），不为对齐指标做额外采集。
- **用量估值**：token 数 × 单价表得出估算金额；单价来源**待定**，先用 M6 中可配置的静态单价表（区分平台/模型、输入/输出/缓存）。

**② 配额 / 余额适配器（`crates/core/adapters/`）**

- **Kimi（`kimi.rs`）**：非官方 `GET /coding/v1/usages`（5h 滚动窗口 + 月度池余量），**best-effort**——接口可能失效，失败降级为"不可用"提示，不影响本地统计。开放平台按量余额 `GET /v1/users/me/balance` 保留。
- **DeepSeek（`deepseek.rs`）**：官方 `GET /user/balance`，按量余额；凭据进 keyring。（用户尚未购买，购买后启用。）
- **MiMo（`mimo.rs`）**：**无公开 API**——M6 手录套餐月度 Credit 总额与计费周期，消耗进度由 mimocode 本地日志推算（已消耗 Credit / 总额 = 进度条），不发任何网络请求。

**前端页面/组件**

- `views/Usage.vue`（原 Kimi.vue 泛化）：平台切换 Tab（总览 / Kimi / MiMo / omp / DeepSeek）+ 总览卡片墙（各平台今日用量、配额/余额、MiMo 套餐进度条）+ 趋势图（ECharts 折线，可按平台过滤）+ 项目/模型分布
- `components/UsageTrendChart.vue`、`components/CacheHitBadge.vue`、`components/QuotaCard.vue`（配额/余额卡片，含"不可用/未配置"降级态）
- `stores/usage.ts`（按平台组织状态）

**Rust 侧命令（Tauri commands）**

| 命令 | 作用 |
|---|---|
| `scan_usage_logs(platform?)` | 增量扫描（不传 platform 则全平台；启动时与定时任务复用同一逻辑），返回 `ScanReport`（含坏行/失败文件计数） |
| `usage_summary(platform, range)` | 聚合总览（天/周/月/最近5小时），`platform='all'` 为跨平台合计 |
| `usage_by_project` / `usage_by_model`（带 platform 参数） | 分组聚合（项目 / 模型） |
| `usage_series(platform, range)` | 时间序列（趋势图；Day 按小时、Week/Month 按日分桶） |
| `quota_refresh(platform)` / `quota_latest(platform)` | 拉取/重算平台配额并写快照 / 读最近快照（MiMo 为本地推算） |
| `platform_account_get` / `platform_account_set` | 各平台账户配置（凭据进 keyring；MiMo 录套餐总额与周期） |

**数据表要点**

- `platform_account(id, platform, name, api_base, credential_ref, quota_total, quota_cycle, enabled)` — 各平台账户；`credential_ref` 是 keyring 里的 key，不是凭据本身；MiMo 用 `quota_total`/`quota_cycle` 手录套餐
- `log_file(id, platform, path, offset, size, mtime, last_scanned_at)` — 增量解析游标（泛化自 `kimi_log_file`）
- `usage_event(id, platform, cli, log_file_id, ts, session_id, project, model, input_other, output, cache_read, cache_creation, cost)` — 只追加；`cost` 可空（日志自带成本时保留，供 MiMo 进度推算）；`log_file_id` 外键用于截断时整批重建
- `usage_daily(date, platform, cli, project, model, input_other, output, cache_read, cache_creation)` — 预聚合，`PRIMARY KEY(date, platform, cli, project, model)`，幂等重算
- `quota_snapshot(id, platform, total, used, remaining, detail_json, fetched_at)` — 配额/余额历史（Kimi 窗口余量、DeepSeek 余额、MiMo 推算进度统一落此表）

**依赖外部接口**：本地文件系统（`~/.kimi-code` / `~/.local/share/mimocode` / `~/.omp`）、Kimi `/coding/v1/usages` 与 `/v1/users/me/balance`、DeepSeek `/user/balance`。

### M2 · 我的 API 平台（已取消，编号保留不复用）

**已取消**。原方案为自建 new-api API 中转网关、软件侧只读展示网关用量。经评估决定放弃，理由：

- 官方套餐直连已够用（Kimi Code 套餐、MiMo Token Plan 各自有 CLI 直连，无需自建中转）；
- MiMo 套餐条款禁止将套餐额度用于非编程工具场景，自建网关转发流量存在合规风险；
- 免去网关的部署与运维负担（阶段二不再部署 new-api）。

原设计（`newapi_admin.rs` 适配器、`gateway_balance_snapshot` / `gateway_usage_cache` 表、`gateway_*` 命令、Gateway 页面）全部作废，不再实现。跨平台用量展示需求并入 M1（多平台用量聚合，只读、不转发流量）。取消网关后 lost 的是跨平台耗时/错误率对比，M1 指标策略为 best-effort（日志里有什么看什么）。M2 编号保留不复用。

### M3 · 服务器（已取消 2026-10-02）

**状态：已取消，编号保留不复用。** 原因：用户近期无时间维护一体机（硬件采购、部署与运维暂缓），被监控/被控制对象短期内不存在；阶段二随之冻结。以下内容保留供历史参考，不再实现。

原计划：阶段二。一体机（Debian 12 + Docker）的监控与基础控制。

**前端页面/组件**

- `views/Server.vue`：主机状态卡片（CPU/内存/磁盘/温度，来自 Netdata）
- `components/ContainerList.vue`：Docker 容器列表 + 启动/停止/重启

**Rust 侧命令**

| 命令 | 作用 |
|---|---|
| `server_overview(host_id)` | 调 Netdata API 取摘要指标 |
| `list_containers(host_id)` / `container_action(id, op)` | Docker 容器查询与操作（SSH 隧道内走 Docker socket） |
| `wake_host(host_id)` | 发送 WOL 魔法包 |

**实现要点**

- WOL：UDP 魔法包，注意 Tailscale 组网与局域网广播的关系——WOL 通常需在同网段或网关转发，**跨网段唤醒方案待定**。

**数据表要点**

- `host(id, name, tailscale_ip, ssh_port, ssh_credential_ref, wol_mac, netdata_port, enabled)` — M3/M4 共用同一条主机记录

**依赖外部接口**：SSH (22)、Docker socket、Netdata (19999)、WOL (UDP 9)。

### M4 · NAS（已取消 2026-10-02）

**状态：已取消，编号保留不复用。** 原因同 M3（用户近期无时间维护一体机，阶段二冻结）。以下内容保留供历史参考，不再实现。

**前端页面/组件**

| 命令 | 作用 |
|---|---|

### M5 · 魔法工具

mihomo 以 Tauri sidecar 形式内置，软件通过其 RESTful API（默认 9090）驱动。阶段一只做核心三件套：**节点切换、系统代理开关、规则组切换**。

**前端页面/组件**

- `views/Proxy.vue`：代理组列表（当前选中节点、延迟着色）、规则组切换开关、系统代理开关
- `components/NodeCard.vue`：节点名 + 延迟 + 测速按钮
- `stores/proxy.ts`：轮询 mihomo API 保持状态同步（mihomo 侧才是事实源）

**Rust 侧命令**

| 命令 | 作用 |
|---|---|
| `proxy_status` | sidecar 存活 + mihomo `/proxies` 摘要 |
| `select_proxy(group, node)` | PUT `/proxies/{group}` |
| `test_delay(group?)` | GET `/proxies/{name}/delay`，批量测速 |
| `set_system_proxy(enabled)` | 写系统代理（Windows 注册表，仅支持 Windows 见 NF-14） |
| `switch_rule_mode(mode)` | 规则组/模式切换（PATCH `/configs` 或按配置文件的策略组选择） |

**实现要点**

- `crates/core/mihomo/client.rs`：mihomo RESTful API 的薄封装，hub 不需要此模块（魔法工具是客户端本地功能，中枢不可达时也必须可用）。
- sidecar 生命周期：Tauri 启动时拉起、退出时回收；端口冲突检测，9090 被占则顺延并写入设置。
- 分流规则（api.openai.com / anthropic.com 强制走稳定节点组）写在注入的 mihomo 配置模板里，软件只负责切换，不运行时改规则——改规则 = 换模板重载，降低复杂度。
- 节点导入（M5-07，2026-10-02 修正优先级）：**订阅链接 + 定时更新为主**（用户当前为商家包月订阅用户；订阅更新失败保留旧节点并告警），手动粘贴分享链接（vless://、hysteria2:// 等）/yaml 片段为辅（后续境外 VPS 自建用）。
- 已知限制（已确认）：阶段一仅系统代理模式，**不做 TUN**——不读系统代理的终端 CLI 流量不经过 mihomo，AI 域名分流对其不生效；TUN 需管理员提权，后续按需评估。**M5 目标场景为软件与网站，不考虑游戏**（2026-10-02 确认）。
- 系统代理开/关必须成对可靠：异常退出后下次启动检测"上次是否遗留开启状态"并提示恢复。

**数据表要点**

- `proxy_setting(key, value)`：当前模式、选中的节点、系统代理状态、订阅地址
- 节点信息不落库，每次从 mihomo API 现取

**依赖外部接口**：mihomo RESTful API (9090)、系统代理设置接口。

|---|---|

| `hub_status` | 中枢连通性探测 + 当前模式 |

**中枢（hub）——架构能力，非独立功能模块**

hub 是同一 monorepo 的另一 Rust 编译产物（`apps/hub`），跑在一体机上，无界面，仅监听 Tailscale 网卡。职责：统一对外采集（各平台配额/余额）、集中存历史、加密存配置并下发、转发控制指令（如 SSH 重启容器）。客户端侧体现为 `DataSource` 的 `HubSource` 实现（`crates/core/datasource/hub.rs`）：

- 离线降级：hub 连续 N 次不可达自动切回 `DirectSource`，`DatasourceBadge` 显示当前模式；M5 魔法工具不走 hub，天然不受影响。
- 配置同步：客户端启动时拉 hub 配置比对版本，冲突策略**待定**（先按"hub 为准"）。
- 本地日志统计（M1 的三类 CLI 日志解析）始终在各客户端本地执行，hub 只汇聚配额/余额类数据；日志数据是否上报 hub 属阶段三增强，**待定**。
- hub 存储：SQLite 起步；是否升级 Postgres **待定**（单用户量级预计不需要）。

**数据表要点**

- `setting(key, value)` — 通用偏好与数据源模式
- hub 侧：`client_config(id, scope, payload_encrypted, version, updated_at)`

**依赖外部接口**：Tailscale 网络（详见《03-部署文档.md》）。

## 5. 开发规范

- **提交信息**：Conventional Commits —— `feat(usage): add omp jsonl incremental parser`、`fix(proxy): restore system proxy on exit`。scope 用模块小写名（usage/server/nas/proxy/settings/hub/core）。
- **分支策略**：个人项目走 trunk-based：直接在 `master` 上小步提交，较大的功能用 `feat/xxx` 短生命周期分支 + 自审 PR（为了跑 CI 和留记录）。tag 即发布。
- **代码风格**：
  - Rust：`rustfmt` + `clippy`（CI 中 `-D warnings`）。
  - TS/Vue：ESLint 9 flat config（`@vue/eslint-config-typescript`）+ Prettier（ESLint 只管规则、Prettier 只管格式，职责分开）。
  - 提交前钩子（已确认，**从简**）：simple-git-hooks + lint-staged，只对本次暂存的文件跑 prettier + eslint --fix，不做全仓检查；全仓检查由 CI 兜底。
- **类型纪律**：`packages/core-types` 只由 ts-rs 生成；前端 invoke 的参数/返回类型必须来自该包。

| 日志解析器（重点） | **fixture 驱动单元测试**：三个 parser 各自的脱敏样本（wire.jsonl / mimocode.db 快照 / omp JSONL，覆盖正常事件、缺 usage、损坏行、空行、多会话多项目）锁定解析行为；专项用例覆盖增量偏移（续读、文件截断后重扫、新增文件发现）与聚合正确性（缓存命中率公式、天/周/月/最近5小时边界、platform 维度分组） | cargo test + fixture |

| Rust 其他逻辑 | 数据源切换、离线降级、WOL 包构造、SSH 命令输出解析（df/smartctl 用录制输出 fixture） | cargo test |

## 7. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 外部 CLI 日志格式随版本漂移：wire.jsonl / mimocode.db / omp JSONL 均为各 CLI 内部格式，未文档化，版本升级可能变更字段 | 对应平台的 M1 统计失效或算错 | parser 容错设计 + 坏行隔离（未知字段忽略、单行失败跳过计数不中断）；fixture 测试锁定当前行为，CLI 升级后跑测试即知是否破坏；单平台解析失败只降级该平台卡片，不影响其他平台与配额功能 |
| Kimi `/coding/v1/usages` 为非官方接口 | 接口随时可能失效或变更 | best-effort 定位：失败降级为"不可用"提示，本地日志统计不受影响；字段解析宽松化 |
| 日志体积随使用增长，事件表膨胀 | 扫描变慢、SQLite 变大 | 增量解析避免重扫；预聚合后事件表可按月归档清理（阶段三打磨项）；最近 5 小时窗口走事件表索引查询 |
| mihomo 内核打包进 Tauri sidecar | 安装包体积增大、杀软误报 | 已确认**仅支持 Windows**（NF-14），只打包 Windows 版 mihomo 二进制，macOS 签名/公证问题不存在；选 mihomo 官方 release 固定版本，升级走配置 |
| 二手硬件 / 一体机到货延期 | 阶段二无法启动 | 阶段一完全不依赖新硬件；hub 可先在笔记本上 Docker 里跑通开发联调，硬件只影响正式部署 |
| NAS 形态未定 | M4 设计悬空 | `NASProvider` trait 隔离，阶段二只做 SSH 直采默认实现（存储占用 + SMART），换方案只换 Provider |
| 系统代理状态残留（软件崩溃后系统代理还开着） | 用户断网、体验事故 | M5 启动自检 + 退出钩子双重保障；写死恢复路径的测试用例 |
| Tailscale 网络异常导致 hub 不可达 | 中枢数据源中断 | 离线降级是设计内行为（见 M6 节），不是异常兜底 |
