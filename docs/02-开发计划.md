# Toogl（图格）开发计划与架构约定

> 本计划以《01-需求文档》为准：首页看板保留并汇总所有模块，魔法工具是核心，网络诊断、系统状态、空间维护和软件设置保持独立边界。
> 实现状态以代码和实际验收为准；计划内容不得标记为已完成。

## 1. 技术边界

- 桌面：Tauri 2，Windows 10/11 + WebView2。
- 前端：Vue 3、TypeScript strict、Pinia、Vue Router、Tailwind CSS 4、shadcn-vue（new-york/neutral）、lucide。
- 核心：Rust stable、sqlx + SQLite、reqwest、Windows 系统 API。
- 工程：pnpm workspace + Cargo workspace；Node 24 LTS；版本由根 `package.json` 的 `packageManager` 锁定。
- 业务核心、解析、持久化、文件扫描和系统能力下沉 Rust；Tauri commands 只装配状态、调用 core 和映射错误。
- 模块采用编译时登记，不引入运行时插件、远程 Hub、空业务抽象或尚无调用方的数据源接口。
- 当前代理只使用 Windows 系统代理，不做 TUN、虚拟网卡和进程级代理。

## 2. 产品模块与目录

```text
apps/desktop/
  src/
    app/
      modules.ts             模块导航、路由和摘要卡唯一登记点
      router.ts              hash 路由
      components/            AppSidebar 和 SidebarLink，应用壳导航组件
    modules/
      dashboard/             首页看板布局，不持有业务公式
      proxy/                 魔法工具：代理、节点、订阅和导入
      network-diagnostics/   固定 DNS/TCP 检查和 DNS 刷新
      system-status/         Windows 和设备只读信息
      storage/               Temp 扫描和空间概况
      settings/              Toogl 主题和版本信息
    shared/                  错误规整、标签同步和小型公共展示能力
    components/ui/           shadcn-vue 组件
    lib/                     通用格式化和 UI 工具
  src-tauri/
    src/commands/            各模块的薄命令层
    src/sidecar.rs           mihomo 生命周期
crates/core/
  src/
    mihomo/                  mihomo REST client
    subscription/            节点解析、拉取、托管文件、更新和回滚
    sysproxy.rs              Windows 系统代理与恢复
    proxy_setting.rs         代理设置和备份持久化
    preferences.rs           普通偏好
    system_tools.rs         Windows 专属系统信息、网络诊断和 Temp 扫描
    db.rs                    SQLite 迁移
    models/                  Rust 跨语言模型和错误契约
  migrations/                只追加的 SQL 迁移
packages/core-types/         ts-rs 生成物及包入口
docs/                        产品、开发和模块接入文档
```

模块可以按实际复杂度省略空的 `api.ts`、`store.ts`、`components/` 层，但不得为了统一目录增加无业务转发。

当前页面已拆分为六个模块目录，旧 `system-tools` 前端聚合页及其标签路由已移除。
`App.vue` 只装配应用壳，`app/components/AppSidebar.vue` 管理导航布局，`SidebarLink.vue` 统一链接样式。
基础模块使用局部 composable 管理状态；系统状态的信息查询同时服务空间维护，不复制 IPC。
目前只有魔法工具提供看板摘要卡，其他模块摘要卡仍属计划，目录完成不等于产品阶段验收完成。
逐模块的调用链、生命周期、修改入口和验证方式由 [AGENTS 维护索引](../AGENTS.md#模块维护入口与文档链路) 汇总，具体指南位于 `docs/modules/`。

## 3. 模块登记和依赖方向

`apps/desktop/src/app/modules.ts` 是业务模块导航、路由和摘要卡的唯一登记点：

- 首页看板和软件设置由 `app/router.ts` 固定定义，侧栏固定展示；其余业务入口从登记表派生。
- 当前业务模块顺序建议为：魔法工具、网络诊断、系统状态、空间维护。
- 数组顺序就是导航顺序，不增加重复排序字段。
- 页面使用动态 import；摘要卡使用 `defineAsyncComponent` 按需加载。
- 看板只遍历登记的摘要卡，不导入模块 Store，不复制业务判断。
- 摘要卡由所属模块实现，直接复用所属模块 API/Store；业务错误在卡片内展示。通用异步加载/渲染异常边界尚未实现，属于看板完善目标。
- 模块配置在所属模块页面中管理；软件设置不依赖业务模块。
- 公共组件不写死业务路由；路由入口由模块提供。

依赖方向：

```text
应用壳 → 模块公开入口 → 模块 Store/API → Tauri commands → crates/core
看板 → 模块 OverviewCard（只布局，不反向持有模块业务状态）
软件设置 ↛ 业务模块
```

## 4. 数据与持久化

### 4.1 SQLite

共享应用数据目录为 `<app_data_dir>/toogl.db`。当前长期数据包括：

- 代理设置、控制端口、secret 和系统代理备份；
- 订阅 URL、订阅节点元信息、手动节点和更新时间；
- `PreferenceStore` 的 app namespace 偏好。

系统状态、网络诊断和空间扫描默认只保留当前模块状态，除非后续需求证明持久化有实际价值。

数据库规则：

- 新迁移创建 `crates/core/migrations/NNNN_description.sql`，并追加 `db.rs::MIGRATIONS`。
- 迁移版本只增不改，历史迁移保留。
- 每条迁移和版本登记在同一事务中；SQL 语句幂等。
- 执行器按分号切分，SQL 字符串字面量内禁止分号。
- 旧值只能在迁移成功后删除；读取失败不能按首次使用覆盖配置。
- 对缩小 UI 范围，不得随意删除仍需兼容的旧 schema。

### 4.2 偏好

- `AppPreferences` 固定使用 `app` namespace，目前保存 theme。
- 缺失记录返回 `null`，与读取错误区分。
- 新字段使用 serde 默认值兼容旧 JSON；复杂结构必须有明确迁移。
- localStorage 只作主题首屏缓存，SQLite 是事实源。
- 工具配置由所属工具管理，不把代理 URL、节点或诊断参数放入软件设置。

### 4.3 生成类型

Rust `models/` 是跨语言类型唯一来源：

- 用 `ts-rs` 导出 `packages/core-types/bindings/`。
- bindings（含 `index.ts`）禁止手改。
- 修改 Rust models 后运行导出测试并审阅生成差异。
- 前端 API、Tauri 参数和返回类型必须与生成契约一致。

## 5. 魔法工具架构

### 5.1 生命周期

应用启动顺序：

```text
WebView2 检查 → 打开数据库/迁移 → 读取偏好 → 启动 mihomo → 装配模块状态 → 进入看板
```

mihomo 启动失败时只让魔法工具降级：

- `proxy_status` 返回启动错误和可读状态；
- 看板显示魔法工具不可用；
- 网络诊断、系统状态、空间维护和设置仍可使用；
- 不自动重启用户配置错误的 mihomo。

### 5.2 代理链路

```text
魔法工具页面/摘要卡
  → proxy Store / subscription Store
  → Tauri commands
  → ProxyCoreState / ProxySettingStore / SystemProxyManager
  → MihomoClient / Windows registry / SQLite
```

事实源：

| 状态 | 事实源 |
| --- | --- |
| mihomo 存活和版本 | mihomo `/version` |
| 代理组和当前节点 | mihomo `/proxies` |
| 规则模式 | mihomo `/configs` |
| 系统代理真实状态 | Windows registry |
| 订阅元信息和手动节点 | SQLite |

本地记忆值只作 mihomo 不可达时的降级展示，不能覆盖实时值。

### 5.3 系统代理安全

- 开启前备份原系统代理状态。
- 开启和关闭使用 `spawn_blocking` 或等价异步边界，不在 Tokio runtime 内嵌套同步 runtime。
- 关闭和正常退出时先恢复系统代理，再杀 sidecar。
- 首次代理状态命令惰性检查异常退出残留。
- 恢复失败必须保留恢复路径和错误信息。
- controller 和 mixed proxy 默认只监听回环，controller 使用随机 secret。

### 5.4 订阅链路

```text
拉取/粘贴
  → 解析
  → 手动节点与订阅节点合并（手动同名优先）
  → 确保 Toogl 节点文件接线
  → 备份并原子写 toogl-nodes.yaml
  → mihomo 热重载
  → 失败原子回滚
  → 成功后写入 SQLite 元信息
```

- 更新与手动导入共享互斥标志，命令和后台任务不能并发修改节点文件。
- 24 小时后台更新由 Rust 管理，不依赖配置页打开。
- 拉取、解析、接线、写文件、热重载任一步失败都保留旧节点。
- 用户手写、无 Toogl 模板标记的配置不得自动改写；接线失败返回手工处理说明。
- 仅提取节点，不覆盖用户完整规则、端口和其他 mihomo 配置。

## 6. 基础模块架构

### 6.1 网络诊断

Rust core 提供固定测试目标的 DNS 查询、TCP 检查和 `ipconfig.exe /flushdns` 调用：

- DNS 最长 5 秒，TCP 最长 3 秒。
- DNS 失败或超时不执行 TCP。
- 前端不能传入任意命令、路径或参数。
- 结果描述测试目标，不推断整个网络。
- 每次诊断为用户主动操作，不默认持续轮询。

### 6.2 系统状态

通过 Windows 只读 API 获取 Windows 版本、设备名、处理器、物理内存和系统盘空间。不得以环境变量代替系统版本事实源，不提供修改系统设置的动作。

### 6.3 空间维护

只扫描当前用户 `%LOCALAPPDATA%\\Temp`：

- 根目录重解析点拒绝扫描；
- 子项符号链接和其他重解析点跳过；
- 限制扫描量和执行时间；
- 不接受任意路径；
- 当前阶段不删除文件。

### 6.4 软件设置

只管理主题和版本信息。不开设未实现的开机自启、窗口行为、置顶、TUN 或代理配置开关。

## 7. 加载、刷新和退出

- 首屏使用主题缓存，随后异步校准 `PreferenceStore`。
- 看板读取模块摘要快照，不启动全局持续轮询。
- 魔法工具页面可见时轮询代理状态，离开时停止；隐藏窗口跳过本轮。
- 网络诊断和空间扫描仅按用户操作执行。
- 初始化请求可复用，避免看板和详情页重复启动相同任务。
- 前端保留可用缓存，后台刷新失败不清空旧值。
- 乐观更新失败必须回滚；过期响应不得覆盖新状态。
- 持续后台任务只在 Rust 装配和清理。
- 正常退出先恢复系统代理，再回收 mihomo；异常退出由下次启动自检兜底。

## 8. 分阶段开发

### 阶段 0：文档与工程收口

目标：让代码入口、模块边界、文档和生成契约一致。

内容：

- 保留首页看板和模块摘要卡。
- 将现有系统工具按产品任务拆分为网络诊断、系统状态、空间维护的模块边界。
- 修复 IPC 命令注册、bindings 漂移和门禁问题。
- 同步文档、路由、模块登记和人工验收口径。

不做：新代理能力、TUN、远程服务、多配置系统。

### 阶段 1：魔法工具基础闭环

目标：启动 mihomo、查看状态、切换节点和模式、开关系统代理、正常退出恢复。

验收：

- 首次启动生成最小配置并可启动 sidecar。
- 节点、代理组和模式状态可读。
- selector 节点可切换，失败可回滚。
- 规则、全局、直连可切换。
- 系统代理开启前备份，关闭和退出时恢复。
- 强制结束后再次启动能识别并恢复残留。
- sidecar 失败不阻塞其他模块。

不做：TUN、PAC、自动选节点、规则编辑、测速历史、多订阅。

### 阶段 2：节点来源和可靠性

目标：完成订阅、手动导入、合并、热重载和回滚。

验收：

- HTTP/HTTPS 订阅可更新。
- 支持约定的 YAML、Base64 和分享链接格式。
- 手动节点优先且坏行隔离。
- 更新失败保留旧节点。
- 热重载失败回滚节点文件。
- 后台 24 小时更新不依赖页面。
- 手写配置不会被静默覆盖。

不做：多订阅管理、节点智能评分、自动最低延迟切换、完整 YAML 编辑器。

### 阶段 3：基础模块和看板完善

目标：看板准确汇总魔法工具、网络诊断、系统状态和空间维护。

验收：

- 首页所有模块状态卡可见。
- 卡片和模块页面使用同一数据口径。
- 模块错误互不阻塞。
- 网络诊断、系统只读信息和 Temp 安全扫描可用。
- 未检查状态不伪装成正常。

不做：自动网络修复、自动清理、全局持续诊断、系统优化开关。

### 阶段 4：真实桌面验收与发布

目标：验证 Windows 10/11、WebView2、sidecar、系统代理、订阅、CSP 和 NSIS 包。

不做：在真实验收前继续堆叠高级功能；不以单元测试替代桌面行为验证。

## 9. 质量门禁

前端：

```powershell
pnpm build
pnpm lint
pnpm format:check
pnpm test:front
```

Rust：

```powershell
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo test -p toogl-core export_bindings
```

打包：

```powershell
pnpm tauri build
```

CI 必须执行前端 lint、格式、测试，Rust fmt、clippy、全量测试、bindings 一致性检查和 Windows NSIS 构建。

## 10. 人工验收

1. 首页看板显示所有模块，魔法工具卡重点突出但其他卡片不隐藏。
2. 看板摘要与对应模块数据一致，模块失败互相隔离。
3. mihomo 启动/退出无孤儿进程。
4. 节点切换后出口变化，规则/全局/直连切换正确。
5. 系统代理开关、关闭恢复和强杀后恢复正确。
6. 真实订阅导入可见，断网刷新保留旧节点。
7. 手动节点和订阅节点合并正确，坏行不拖垮有效节点。
8. 网络诊断、系统状态和 Temp 扫描不越过各自安全边界。
9. 生产 NSIS 包资源加载正常，CSP 无错误。
