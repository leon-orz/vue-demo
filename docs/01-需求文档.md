## 1. 项目背景与目标

### 1.1 背景

这是一个**个人自用**的 PC 桌面工具箱软件（正式名 **Toogl**，中文名"**图格**"），把作者日常散落在各处的工具集中到一个应用里。当前存在三大痛点：

1. **AI 用量看不清**：作者同时使用多个 AI 编程平台/套餐——Kimi Code 套餐（kimi-code CLI）、小米 MiMo Token Plan（mimo / omp CLI）、oh-my-pi（omp，可接 MiMo/DeepSeek 等上游）、DeepSeek 按量（后续可能买）。用量散落在各 CLI 的本地日志里（kimi-code 的 `wire.jsonl`、MiMo Code 的 `mimocode.db`、omp 的会话 JSONL），没有统一聚合视图，token 消耗、缓存命中率、配额余量都看不到；各平台余额/配额要分别登录网页查询。
2. **设备控制分散**：计划 DIY 一台台式机作为"一体机"（NAS + 服务器一体），看监控要开 Netdata 页面、管容器要 SSH 上去敲命令、远程开机要另外发 WoL 魔法包，入口零散。
3. **代理管理分散**：有境外 VPS 自建代理（稳定 IP，专给 Codex/Claude 等编程工具使用），节点切换、系统代理开关、按域名分流都要手动操作 Clash 系客户端，不够顺手。

### 1.2 目标

| # | 目标 | 衡量方式 |
|---|------|---------|
| G1 | 各 AI 平台用量一目了然 | 打开软件即可看到今日/本周/本月 token 消耗、缓存命中率、按平台/CLI/模型/项目分布，无需翻日志 |
| G2 | 各平台配额/余额统一展示 | Kimi 5 小时窗口与用量（best-effort）、MiMo 配额（手录+推算）、DeepSeek 余额在软件内可查，无需登录网页 |
| G3 | 一体机的监控、容器管理、远程开关机在软件内完成 | 不再单独打开 SSH 终端 / Netdata 页面 |
| G4 | NAS 存储占用、磁盘健康、共享与备份状态在软件内可查 | 不再登录一体机逐个查 |
| G5 | 魔法工具核心三样（节点切换、系统代理开关、规则组切换）+ 延迟测试 + AI 域名分流在软件内完成 | 不再单独打开 Clash 客户端面板；api.openai.com / anthropic.com 等域名强制走稳定节点组 |
| G6 | 多设备协同：笔记本、台式机数据一致，中枢不可达时本地功能不受影响 | 切换设备后配置与历史数据一致；断连中枢时魔法工具等本地功能正常 |

### 1.3 非目标

见第 7 章"范围边界"。

## 2. 名词解释

| 名词 | 通俗解释 |
|------|---------|
| wire.jsonl | Kimi Code 在本机写的会话日志文件（位于 `~/.kimi-code/sessions/**/`），每行一条 JSON 记录，每次 API 请求的记录里带 usage 字段。是本软件 Kimi 用量统计的数据源。 |
| usage 字段 | wire.jsonl 中每次请求的用量记录：`inputOther`（普通输入 token）、`output`（输出 token）、`inputCacheRead`（缓存命中 token）、`inputCacheCreation`（缓存写入 token）。 |
| 缓存命中 / 缓存写入 | Kimi 的上下文缓存机制：命中缓存的输入 token（inputCacheRead）单价更低；首次写入缓存的 token（inputCacheCreation）单独计价。缓存命中率是衡量用量成本效率的关键指标。 |
| 5 小时滚动窗口 | Kimi Code 包月的限流窗口：官方按最近 5 小时内的用量限制速率。软件用本地日志聚合出"最近 5 小时用量"作为近似值。 |
| Kimi Code 套餐 | Kimi 官方编程订阅套餐（kimi-code CLI 使用）：5 小时滚动窗口限流 + 月度池。用量接口为非官方 `GET /coding/v1/usages`，best-effort 查询。 |
| 小米 MiMo Token Plan | 小米官方 AI 编程订阅套餐：月度 Credit 池。主要 CLI 为 mimo（MiMo Code CLI），也可经 omp 接入。无公开配额查询 API，采用"手录总额 + 本地日志推算消耗"。注意其条款禁止套餐额度用于非编程工具场景。 |
| MiMo Code（mimo） | 小米的 AI 编程 CLI。本地日志为 SQLite 数据库 `~/.local/share/mimocode/mimocode.db`，message 表 data JSON 含 tokens/cost/modelID/providerID。本软件只读打开该库，绝不写入。 |
| oh-my-pi（omp） | 第三方 AI 编程 CLI（非套餐），可接 MiMo/DeepSeek 等上游，计费随上游平台。本地日志为 `~/.omp/agent/sessions/**/*.jsonl`，assistant 行带 usage（input/output/cacheRead/cacheWrite）+ provider/model + timestamp + stopReason 错误。 |
| one-api / new-api（历史决策） | 开源 AI API 网关项目。本项目曾计划用 new-api 自建中转网关（原 M2），已取消：官方套餐直连已够用、MiMo 条款禁止套餐额度用于非编程场景、免去网关运维负担。 |
| 中枢服务（hub） | 跑在一体机上的无界面后台服务（Rust，与客户端同一项目的另一编译产物）。负责集中存历史、加密存配置并下发、转发控制指令（如 SSH 重启容器）。 |
| 直连模式 | 中枢不可达（或尚未部署）时，客户端自己直连各平台官方 API / 一体机、本地存数据的运行模式。 |
| 中枢模式 | 中枢在线时，客户端经中枢存取数据、由中枢下发配置的运行模式。 |
| mihomo | Clash 系代理内核（原 Clash.Meta），提供 RESTful API（默认 9090 端口）。软件把它作为 sidecar 内置，实现节点切换、延迟测试、系统代理开关、按域名分流。 |
| 系统代理 | 操作系统级的代理开关，打开后大部分应用的流量自动走代理。 |
| 规则组 / 分流 | 按域名等规则决定流量走哪个节点或直连。本项目要求 api.openai.com、anthropic.com 等域名强制走"稳定节点组"。 |
| Tailscale | 组网工具，把多台设备组成一个私有网络。所有设备用它互联，中枢不开公网端口。 |
| WoL（Wake-on-LAN） | 局域网远程开机：向关机设备的网卡发"魔法包"把它唤醒。 |
| Netdata | 服务器监控工具，输出 CPU、内存、温度、网络等实时指标。 |
| SMART | 硬盘的自我监测数据（通电时间、坏道、温度等），用于判断磁盘健康。 |
| Tauri 2 | 用 Web 前端 + Rust 后端构建轻量桌面应用的框架。 |
| 钥匙串 | 操作系统自带的凭据安全存储（Windows 凭据管理器、macOS Keychain 等），用于加密保存敏感 key。 |
| 3-2-1 备份 | 至少 3 份数据、2 种不同介质、1 份异地/离线。 |

## 3. 用户与设备角色

**用户**：单一用户（作者本人），个人自用，无多用户、无权限体系。

### 3.1 设备角色

| 设备 | 角色 | 运行内容 |
|------|------|---------|
| 笔记本 | 全功能客户端 | Toogl 桌面客户端（Tauri 2 + Vue 3） |
| 台式机 | 全功能客户端 | Toogl 桌面客户端（同上） |
| 一体机（DIY 台式机） | 中枢 + 被控对象（服务器 & NAS） | 中枢服务（hub，无界面）、Netdata、Samba/NFS、Tailscale、可选 Cockpit；同时作为 M3 被监控/被控制的服务器和 M4 被管理的 NAS |
| 境外 VPS | 代理出口 | 只跑代理服务端（mihomo/sing-box），Tailscale 组网 |

### 3.2 角色关系说明

- 客户端是功能入口，本地可独立完成 AI 用量统计（CLI 日志解析）、魔法工具等功能。
- 中枢是"数据中枢 + 控制中转"：在线时客户端走中枢模式；不可达时客户端自动切直连模式（见 5.6 架构能力）。
- 一体机同时承载 M3（服务器）与 M4（NAS）两个模块的管理对象，但两个模块在软件内**逻辑上完全独立**。
- VPS 不参与统计与控制链路，只作为魔法工具的代理节点来源。

### M2 （已取消）我的 API 平台

**状态：已取消，编号保留不复用。** 原需求为自建 new-api 中转网关的用量只读展示（原 M2-01~07 全部作废）。

取消决策与原因：

1. **官方套餐直连已够用**：作者的 AI 编程用量集中在 Kimi Code 套餐、小米 MiMo Token Plan 等官方订阅，客户端直连官方/半官方接口 + 本地 CLI 日志即可覆盖统计需求，无需自购账号做渠道中转。
2. **MiMo 条款风险**：MiMo Token Plan 条款禁止套餐额度用于非编程工具场景，自建网关转发流量存在合规风险。
3. **免去网关运维负担**：不再部署、维护 new-api 实例（渠道配置、key 发放、升级等）。

原"按 key/按模型用量统一查看"的统计需求已并入 M1（多平台用量聚合，只读、不转发流量）。

| M5-03 | 系统代理开关 | P0（阶段一） | 核心三样之一 |
| M5-04 | 规则组切换 | P0（阶段一） | 核心三样之一 |
| M5-05 | AI 域名分流：api.openai.com、anthropic.com 等强制走"稳定节点组" | P0（阶段一） | 稳定 IP 专给 Codex/Claude 使用 |
| M5-06 | 延迟测试 | P1（阶段一） | |

## 5. 非功能需求

### 5.1 安全

| 编号 | 需求 |
|------|------|
| NF-01 | 所有敏感凭据（Kimi / DeepSeek 等平台 API key、MiMo 配额配置、SSH 认证信息等）加密存操作系统钥匙串，**不以明文写入配置文件或 SQLite**。 |
| NF-02 | 中枢与客户端、各设备之间通信走 Tailscale 私有网络，**中枢不开公网端口**。 |
| NF-03 | AI 用量数据全部**本地采集**（CLI 日志）+ 平台官方/半官方 API **直连**，不经任何中转/网关转发。 |
| NF-04 | mihomo 的 RESTful API 只监听本机回环地址，不对外暴露。 |
| NF-05 | Docker 控制走 SSH 隧道 + Docker socket，不在一体机上额外暴露 Docker TCP 端口。 |

### 5.2 性能

| 编号 | 需求 |
|------|------|
| NF-06 | 客户端常驻内存目标 **< 200MB**（不含 mihomo sidecar；sidecar 自身开销单独观察，暂不设硬指标）。 |
| NF-07 | Dashboard 与各模块页打开即读本地缓存，拉数/解析异步进行，不阻塞界面。 |
| NF-08 | CLI 日志解析必须增量进行（记录已解析位置/偏移），日志文件增大后每次刷新只读增量部分。 |

### 5.3 可扩展性

| 编号 | 需求 |
|------|------|
| NF-09 | 数据获取层做成可替换接口（DataSource）：直连数据源、中枢数据源对上层透明。 |
| NF-10 | M3/M4 的控制动作做成可扩展的插件式动作，为 NAS 形态变化和后续主机扩展预留。 |

### 5.4 可靠性

| 编号 | 需求 |
|------|------|
| NF-11 | 中枢不可达时客户端自动降级直连模式，本地功能（尤其 AI 用量统计、魔法工具）不受影响。 |
| NF-12 | 单个数据源失败（如某平台 API 超时、某次日志解析异常）不影响其他模块展示，失败状态在界面上可见。 |
| NF-13 | 解析外部 CLI 日志（wire.jsonl / mimocode.db / omp JSONL）必须**容错**：格式随 CLI 版本变化可能出现异常行/异常字段，跳过并计数，不中断整体解析。 |

### 5.5 平台支持

| 编号 | 需求 |
|------|------|
| NF-14 | 客户端目标平台：**仅 Windows**（已确认，作者设备均为 Windows；macOS/Linux 桌面端不做）。 |

### 5.6 架构能力：中枢模式与离线降级

（原"配置与数据同步"模块不再作为独立功能模块，降为架构能力；UI 入口在 M6-03/M6-04。）

| 编号 | 需求 |
|------|------|
| NF-15 | **中枢模式（主）**：中枢服务集中存历史数据、加密存配置并下发到各客户端；控制指令（如 SSH 重启容器）可经中枢转发。 |
| NF-16 | **直连模式（降级）**：中枢不可达或未部署时，客户端自动切回直连——自己直连各平台官方 API / 一体机拉数，配置与缓存用本地 SQLite。恢复在线后自动切回。 |
| NF-17 | 两种模式对功能模块透明，模块只面向 DataSource 接口编程（与 NF-09 呼应）。 |
| NF-18 | 双模式并行期间的数据合并/冲突处理策略待定（倾向以中枢为准）。 |
| NF-19 | mimocode.db（MiMo Code 的 SQLite 日志库）必须以**只读方式**打开，任何情况下不得写入或修改该文件（建议以只读模式打开连接并避免产生 WAL/锁残留）。 |

## 6. 硬件环境规划

> 本章是需求层面的硬件前提，采购与装机细节见《03-部署文档》。

### 6.1 一体机（DIY 台式机，预算约 ¥3500 不含机械盘）

| 部件 | 规划 | 用途/理由 |
|------|------|----------|
| CPU | i5-13400 / R5 7600 | 跑 Docker 服务、文件服务足够；核显可亮机 |
| 主板 | B760 / B650 | 预留 PCIe x16（显卡升级位）、4~6 个 SATA、2.5G 网口 |
| 内存 | 64GB DDR5（2×32GB 双通道） | 多服务 + 后续本地模型余量 |
| 系统盘 | 1TB NVMe | 系统 + Docker 数据 |
| 数据盘 | 机械硬盘按需加（4TB 约 ¥550/块） | NAS 存储，按需扩展 |
| 电源 | 450~850W 金牌 | 为后续加显卡留余量 |
| 机箱 | 多盘位（乔思伯 N2/N3 类） | 多硬盘位 |
| 系统 | Debian 12 + Docker | 跑中枢、Netdata、Samba/NFS、Tailscale，可选 Cockpit |

一体机一挂全挂，**重要数据遵循 3-2-1 备份**：本地 + 移动硬盘/网盘冷备（备份状态在 M4-04 中可见）。

### 6.2 境外 VPS

只跑代理服务端（mihomo/sing-box），Tailscale 组网。不承担其他职能。

### 6.3 本地大模型（可选项，暂不做）

- 主板预留 PCIe x16 插槽和电源余量，以后可加二手 RTX 3090 24GB（约 ¥5000）+ Ollama。
- 模型若后续接入，由 omp 等 CLI 直连本地 Ollama，其用量随 omp 日志自然进入 M1 统计，软件侧无需单独界面。
- 不上显卡时，CPU 舒适区是 4B~8B 及 MoE 模型（如 Qwen3-30B-A3B）。
